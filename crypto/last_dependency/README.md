# Последняя зависимость | Hard | crypto

## Информация

> В журнале ALICE сохранились четыре таблицы точек и дерево проверенных равенств. Каждая запись дерева связывает две точки, но ни одна не замыкает цепь. Последнюю строку журнала вырвали: её левая часть использовала по одной точке из каждой таблицы.
>
> Восстановите эту строку и откройте запись о перезапуске.
>
> nc `<ip>:34212`.

## Деплой

Каталог `deploy/` самодостаточен. Флаг уже указан в `docker-compose.yml`:

```sh
cd deploy
docker compose up --build -d
```

Контейнер выдаёт отдельный случайный реестр на каждое TCP-подключение и принимает один ответ в течение 888 секунд. Копия `src/` внутри `deploy/` обновляется командой `python3 scripts/sync_task_deploy.py` из корня репозитория.

## Выдать участникам

[FORMAT.md](public/FORMAT.md), [sample.bin](public/sample.bin) и адрес TCP-сервиса. Каталоги `src/` и `solve/` не выдавать.

## Описание

Каждое подключение создаёт новый реестр из 24 576 точек Ristretto255, разбитых на четыре таблицы по 6144 точки. Для точек существует 24 575 действительных равенств вида `A_child−A_parent=[u]G+[v]Q`. Они образуют дерево, поэтому исключить все неизвестные точки и получить скаляр `d` из `Q=[d]G` пока нельзя. Отсутствующая строка имеет вид `A₀+A₁−A₂−A₃=[target_u]G+[target_v]Q`, где `Aᵢ` берётся из таблицы `i`. В открытых данных нет четырёх номеров. После их восстановления строка замыкает линейную зависимость. Только правильный скаляр, отправленный до истечения 888 секунд, открывает запись ALICE.

Идея относится к цепочке «базы точек → поиск отношения → исключение точек», описанной в [A Subexponential Time Algorithm for Elliptic Curve Discrete Logarithm](https://github.com/bochum-crypto/subexponential-ecdl/blob/main/subexponential-ecdl.pdf). Статья даёт условный асимптотический результат, а не готовую практическую атаку на Ristretto255; эта задача использует специально созданный неполный реестр и не заявляет ускорения общего ECDLP.

## Решение

1. Прочитать бинарный формат. Проверить, что точки корректны и равенство последней строки даёт указанную `target_point`.
2. Найти отсутствующую четвёрку через meet-in-the-middle: записать все `6144² = 37 748 736` сумм `A₀+A₁`, затем искать совпадения с `target_point+A₂+A₃`. Хешировать сжатые точки, но проверять совпадение полных точек. У задачи одна намеренно созданная четвёрка.
3. Для каждого ребра дерева выразить скаляр точки как `log_G(A_i)=c+α_i+β_i d`, где неизвестная константа `c` относится к корню. Дерево задаёт `α_i` и `β_i` через сумму коэффициентов вдоль пути к корню.
4. В последней строке два плюса и два минуса уничтожают `c`. Если `A=α₀+α₁−α₂−α₃`, `B=β₀+β₁−β₂−β₃`, то `target_u+target_v·d=A+B·d`. Отсюда `d=(A−target_u)/(target_v−B)` по модулю порядка группы. Проверить `[d]G=Q`.
5. Передать `d` серверу в виде 32 байт little endian, записанных шестнадцатерично. Сервер сверит его с `Q` и вернёт флаг и улику. [Локальный образец](public/sample.bin) дополнительно позволяет проверить вывод ключа и тег XChaCha20-Poly1305 без сервера.

[Авторский решатель](solve/src/main.rs) написан на Rust и использует `curve25519-dalek`. Собрать его до подключения: `cargo build --release --manifest-path solve/Cargo.toml`, затем запустить [сетевой сценарий](solve/solve_live.py): `python3 solve/solve_live.py <ip> 34212`. На тестовой машине два полных поиска по таблицам размера 6144 заняли 349 и 388 секунд; число зависит от положения скрытой четвёрки и нагрузки процессора.
