# Решение задачи «Контур управления»

## Общая информация

- **Уровень:** Hard
- **Категория:** web
- **Уязвимости:** SSRF с многослойным фильтром, слепым к IPv6 + находка внутреннего API среди decoy-путей + утечка секрета в большом массиве метрик + IDOR в выдаче пропуска (JWT с повышенным статусом) + IDOR-перебор скрытой записи реестра по большому диапазону id
- **Вектор атаки:** скрытый SSRF (через фоновый unfurl-запрос по ссылке в тексте карточки) → фаззинг внутреннего сервиса среди шума decoy-эндпоинтов → токен обслуживания, спрятанный в многотысячной простыне метрик → IDOR в выдаче пропуска → подмена сессионной cookie на выданный JWT со статусом Operator → реестр → перебор id скрытой записи в диапазоне 1..15000 → флаг

---

## Шаг 0. Оракул SSRF — не там, где кажется

На `/cards` нет поля «источник (URL)». Карточка аномалии — это просто свободный текст в поле «Описание». Но если открыть исходник страницы (`view-source` или DevTools), видно: textarea слушает `input`, регуляркой ищет в тексте что-то похожее на `https?://...`, и если находит — с задержкой ~600мс дёргает в фоне `GET /cards/preview?source_url=<найденная-ссылка>` и показывает результат под полем, без всякой кнопки «отправить». Это и есть unfurl-превью а-ля мессенджеры — и одновременно единственная точка входа SSRF.

`GET /cards/preview?source_url=` — сам по себе stateless-эндпоинт: сервер скачивает URL и возвращает JSON `{"status": <upstream-код>, "preview": <первые ~6 КБ ответа>}`, зеркаля upstream-статус в HTTP-код собственного ответа:

```sh
curl 'http://TARGET:63401/cards/preview?source_url=<любой URL>' -H "Cookie: access_token=<JWT>"
```

`POST /cards/create` (реальное сохранение карточки) при сохранении сам ищет ссылку в описании тем же способом и фетчит её для превью в карточке — так что поле для атаки формально не нужно вообще, достаточно написать текст со ссылкой внутри.

## Шаг 1. SSRF через отсутствие фильтра к IPv6

Фильтр на `source_url` состоит из четырёх слоёв, и каждый из них думает только про IPv4:

1. Строковый чёрный список по адресу: `127.`, `localhost`, `0x`, `0.0.0.0`, `::1` — если подстрока найдена, 403.
2. Запрет литеральных IP: проверка идёт через `ipaddress.IPv4Address(host)` — если строка парсится как IPv4-адрес, 403; доменные имена разрешены.
3. Схема — только `http`/`https`.
4. Перед запросом — resolve хоста и проверка результата на принадлежность приватным IPv4-диапазонам (`10/8`, `127/8`, `172.16/12`, `192.168/16`, `169.254/16`).

Наивная попытка `http://[::1]/` отваливается на первом же слое — подстрока `::1` в чёрном списке. Но тот же адрес loopback можно записать иначе, без этой подстроки:

```
http://[0:0:0:0:0:0:0:1]/
http://[::0:1]/
```

Оба варианта проходят все четыре слоя: подстрок из чёрного списка нет, под `IPv4Address` не парсится (это IPv6), схема `http`, а резолв отдаёт `::1`, которого нет ни в одной IPv4-сети из проверки. Запрос реально улетает на loopback на стандартный порт `80` (в URL его указывать не нужно) — там административный сервис, слушающий только `127.0.0.1:80` и `::1:80` (две одинаковые привязки одного процесса — разработчики никогда не думали про IPv6, поэтому и забыли закрыть его в фильтре).

## Шаг 2. Фаззинг внутреннего API среди шума

Через эндпоинт `GET /cards/preview` прогоняем словарь путей. Поскольку эндпоинт зеркалит upstream-статус, внутренние 404 приходят к нам как HTTP 404 — можно фильтровать штатно. Рекурсию делаем вручную в три уровня:

```sh
curl -s -c jar -X POST http://TARGET:63401/register -d 'username=f&password=f12345' >/dev/null
curl -s -c jar -X POST http://TARGET:63401/login    -d 'username=f&password=f12345' >/dev/null
JWT=$(grep access_token jar | awk '{print $7}')

ffuf -w /usr/share/seclists/Discovery/Web-Content/raft-medium-words.txt:FUZZ \
  -u 'http://TARGET:63401/cards/preview?source_url=http%3A%2F%2F%5B%3A%3A0%3A1%5D%2FFUZZ' \
  -H "Cookie: access_token=$JWT" -fc 404
```

На каждом уровне находится много «живых» (не-404) путей, большинство из них тупиковые:

- **Уровень 1** (`/FUZZ`): `status`, `health`, `version`, `debug`, `private`, `docs`, `admin` — семь хитов, из них реально ведёт дальше только `admin` (в ответе намёк: «часть процедур переведена в регламентный контур обслуживания»).
- **Уровень 2** (`/admin/FUZZ`): `metrics`, `config`, `maintenance`, `logs`, `health`, `cache`, `queue`, `jobs`, `backup`, `debug` — десять хитов, из них нужны три: `metrics`, `config`, `maintenance`.
- **Уровень 3** (`/admin/maintenance/FUZZ`): `ping`, `requests`, `issue`, `status`, `health`, `jobs` — шесть хитов, `requests` и `issue` без токена отвечают `403 maintenance token required (see /admin/config)`, остальное — тупики.

## Шаг 3. Токен обслуживания — спрятан в тысячах строк метрик

`/admin/config` называет заголовок для токена:

```json
{"maintenance_header": "X-Maintenance-Token", ...}
```

Через SSRF заголовок не поставить (мы контролируем только URL, не хедеры исходящего запроса). Угадывать запасной канал не нужно — это известная практика: сервисы, рассчитанные на то, что заголовок иногда поставить нельзя, обычно принимают тот же токен в query (`?token=`, `?access_token=`, `?api_key=` — здесь работает любое из трёх).

Значение токена — в `/admin/metrics`: ответ — несколько тысяч, отсортированных примерно по алфавиту префикса метрики (`cache_*`, `db_pool_*`, `gc_*`, `http_requests_*`, `maintenance_*`, `network_*`, ...). Превью эндпоинта показывает первые ~6 КБ, и нужная строка лежит где-то в районе 140-й строки:

```
maintenance_checks_total 884
maintenance_last_rotation_seconds 1200
maintenance_token_rotated{value="<TOKEN>"} 1
```

При беглом просмотре первых строк (сплошные `cache_*`/`db_pool_*`/`gc_*`) это легко принять за шум и проскроллить мимо. Логичный путь: сначала увидеть `/admin/config` с именем заголовка, понять, что нужно значение, и только тогда вернуться к `/admin/metrics` и искать по слову «token» (Ctrl+F) — а не читать всю простыню построчно с первого раза.

Передаём его в query внутреннего URL.

## Шаг 4. IDOR в выдаче пропуска

С токеном `/admin/maintenance/requests` отдаёт список заявок:

```json
{"requests": [
  {"request_id": 1012, "requested_by": "dr_demon", "room": "архив", "note": "заявка подана 2017-11-02"},
  {"request_id": 1013, "requested_by": "mr_fade", "room": "склад", "note": "заявка подана 2018-01-14"},
  {"request_id": 1027, "requested_by": "mr_s", "room": "наблюдательная", "note": "заявка на продление допуска"},
  {"request_id": 1035, "requested_by": "oper_2011", "room": "серверная", "note": "заявка из старого контура, до миграции"},
  {"request_id": 1041, "requested_by": "oper_2018", "room": "серверная", "note": "заявка подана перед инцидентом"}
]}
```

Далее необходимо вызвать `issue` по каждому `request_id` и посмотреть на ответ:

```json
{"status": "issued", "token": "<PASS_JWT>"}
```

Перебор по всем пяти `request_id` даёт три разных исхода: `1012`/`1013` — честный `403 request is not approved`; `1027`/`1035` — токен **выдаётся**, но смотреть надо не на факт успеха, а на claim внутри самого JWT — там `"status": "Observer"`, то есть пропуск не привилегированный; и только `1041` даёт `"status": "Operator"`.

Заголовок `X-Internal-User: alice` (или `?internal_user=alice`) можно не трогать — это мёртвая приманка, добавляет в ответ `"identity": "accepted"`, но ни на что не влияет.

## Шаг 5. Реестр

Полученным `<PASS_JWT>` просто **подменяем свою же cookie `access_token`**. После подмены `/registry` открывается — три обычные записи допуска 001/002/003. Обратно свой обычный `access_token` (status `Observer`) для реестра не подходит — `require_operator` отдаёт `403 Недостаточно допуска`.

На странице реестра есть ещё два элемента, которые выглядят как потенциальные уязвимости, но ими не являются: сортировка по клику на заголовок колонки (`?sort=`, безопасно — белый список колонок) и «экспорт в CSV» с параметром имени файла (`?filename=`, тоже безопасно - white list). Оба — тупиковые приманки, не часть вектора.

## Шаг 6. IDOR в реестре — перебор id

`/registry` показывает только три записи. Запись с флагом лежит где-то в диапазоне `1..15000`, сгенерированном случайно при первом старте инстанса. `/registry/entry?id=` отдаёт **любую** запись по номеру, не проверяя, должна ли она быть видна. Перебираем диапазон:

```python
from concurrent.futures import ThreadPoolExecutor

def probe(entry_id):
    r = session.get(f"{BASE}/registry/entry", params={"id": entry_id})
    if r.status_code == 200:
        return entry_id, r.text

with ThreadPoolExecutor(max_workers=64) as pool:
    ...  # см. solver.py
```

Найденная запись — допуск 000, «резервный, не выдан», оператор `[———]`, история входов и флаг.
