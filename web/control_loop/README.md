## Описание

Публичный терминал с регистрацией наблюдателя, карточками аномалий и реестром личного состава, закрытым для обычной учётной записи. Во внутреннем контуре, недоступном снаружи, крутится административный сервис контроля — до него можно дотянуться только через фоновый SSRF-запрос, спрятанный в логике карточек. Цель участника — пройти весь контур и найти скрытую запись реестра с флагом.

## Решение

Коротко: **скрытый SSRF → фаззинг внутреннего API среди decoy-путей → токен из метрик → IDOR в выдаче пропуска → подмена сессии на JWT со статусом Operator → IDOR в реестре.**

1. **Скрытый SSRF.** Ссылка в тексте карточки аномалии в фоне скачивается через `GET /cards/preview?source_url=`. Фильтр не знает про IPv6 — `http://[::0:1]/` обходит все четыре слоя и резолвится в loopback (порт `80`).
2. **Фаззинг внутреннего сервиса** через тот же эндпоинт, среди decoy-путей: нужны `/admin/metrics`, `/admin/config`, `/admin/maintenance`, `/admin/maintenance/requests`, `/admin/maintenance/issue`.
3. **Токен обслуживания.** Имя заголовка — в `/admin/config`, запасной канал — `?token=`. Значение — в `/admin/metrics`, спрятано в простыне из тысяч строк.
4. **IDOR в выдаче пропуска.** `/admin/maintenance/issue` выдаёт пропуск по чужому `request_id` без проверки принадлежности — JWT со `status: Operator`.
5. **Реестр.** Подменяем cookie `access_token` на выданный пропуск — открывается `/registry`.
6. **IDOR в реестре.** Флаговая запись скрыта из списка, но `/registry/entry?id=` отдаёт любую запись по id без проверки видимости — id случайный в диапазоне 1..15000, находится прямым перебором.

Полный разбор по шагам — в [solve/solution.md](solve/solution.md), готовый эксплойт — в [solve/solver.py](solve/solver.py).
